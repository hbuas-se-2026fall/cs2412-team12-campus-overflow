## 0. 一分钟概览

这是一个按 **DDD 限界上下文物理分包** 的校园问答系统：

| 维度 | 数字 |
|---|---|
| 后端模块 | 7 个（父 POM + 6 个上下文/装配模块） |
| 后端 Java 文件 | 144 个（含测试） |
| 前端 TS/TSX 文件 | 52 个 |
| 数据库迁移 | 2 个（V1 初始、V2 Sprint 3） |
| 自动化测试 | 50 个（聚合 38 + 接口 12），另有 2 个 Playwright 端到端 |

三条主线：**聚合保护不变式 → 应用服务编排用例 → 领域事件跨上下文协作**。

## 2. 目录地图（先看这一张表）

```
campus-overflow/
├── pom.xml                    父 POM：统一 Spring Boot / JDK / 插件版本
├── co-shared-kernel/          共享内核：聚合根基类、领域事件、异常、UserId、Tag 词表
├── co-identity/               身份上下文：User 聚合（注册/验证/禁用）
├── co-qa/                     问答核心：Question / Answer / Vote / Comment（本项目主体）
├── co-reputation/             声誉上下文：事件驱动的积分账本
├── co-discovery/              发现上下文骨架：读模型（Sprint 4 落地）
├── co-bootstrap/              装配层：启动入口、Flyway、全局异常、JSON 日志、跨上下文适配器
├── frontend/                  React 18 + TS 5 + Vite 6
├── docs/
│   ├── adr/                   ADR-002 分层与分包、ADR-003 Sprint 3 关键设计
│   ├── retro/                 Sprint 回顾纪要
│   ├── lab4|5|6/              每个 Lab 的验证记录与分工
│   └── api/                   openapi.yaml + Postman 集合
└── README.md                  项目说明与 API 清单
```

每个后端模块内部固定四层：`domain / application / infrastructure / interfaces`。
依赖方向：`interfaces → application → domain ← infrastructure`，跨上下文只通过事件或端口。

## 5. 怎么跑起来（老师自己验证用）

```bash
# 1) 数据库（空库即可，表由 Flyway 建）
mysql -uroot -p -e "CREATE DATABASE campus_overflow DEFAULT CHARACTER SET utf8mb4"

# 2) 后端（默认连 127.0.0.1:3306，账号密码可用 DB_USERNAME/DB_PASSWORD 覆盖）
mvn clean install
java -jar co-bootstrap/target/campus-overflow.jar

# 3) 前端（另开终端）
cd frontend && pnpm install && pnpm dev
# 打开 http://localhost:5173
```

**自证命令**（输出应全绿）：

```bash
mvn clean install          # 50 个测试，BUILD SUCCESS
cd frontend && pnpm lint && pnpm typecheck && pnpm build
cd frontend && pnpm e2e    # 需要后端已启动；2 passed
```

## 6. 老师常问的 8 个问题（附答案）

1. **为什么按上下文切模块，而不是按 controller/service/dao 切？**
   编译期就能挡住"问答上下文直接 new 一个 User"。详见 ADR-002 §2 与被否方案表。

2. **聚合怎么防止变成贫血模型？**
   `Question` 没有 setter，只有工厂方法与业务方法，每个方法内联不变式；单测逐条覆盖。

3. **投票为什么不放在 Question 里？**
   热点问题会把投票串行化。投票独立成聚合，票数是目标上的投影（ADR-003 §2）。

4. **声誉为什么不在投票代码里直接加分？**
   那会让问答依赖声誉上下文。改成领域事件 + `AFTER_COMMIT` 监听 + `REQUIRES_NEW`，失败不影响投票（ADR-003 §3）。

5. **事件重复投递会不会重复加分？**
   每条明细有 `event_id` 唯一键，`ReputationAccount` 先判重再落库（`INV-R-02`）。

6. **改判采纳后旧作者的分数怎么办？**
   事件带 `previousAnswerAuthorId`，监听器写一条 `ACCEPT_REVERSED = −15` 的冲正明细，不删旧账。

7. **标签为什么允许用户新建？原来的 INV-Q-02 不是要求必须在词表内吗？**
   US-10 的验收标准要求"新标签自动创建"。这是一次有意识的契约修订，ADR-003 §5 有取舍说明。

8. **测试为什么用 H2 而不是直接连 MySQL？**
   让 `mvn clean install` 不依赖本地数据库；真实 MySQL 的迁移与写入由 `docs/lab4|lab6/验证记录.md` 单独验证。
