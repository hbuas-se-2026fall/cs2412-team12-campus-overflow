# 团队代码评审清单 v1.0

> 第 12 组 · Lab 7 Step 4 产出｜适用：CampusOverflow 全部 PR
> 使用方式：评审人按六类逐项过一遍；只要有一项「必须改」没解决，就不给 LGTM。
> 每条都配了「在本项目里长什么样」的例子，避免清单变成口号。

---

## 0. 使用约定

| 标记 | 含义 |
|---|---|
| 🔴 必须改 | 阻塞合并：正确性、安全、契约破坏 |
| 🟡 建议改 | 不阻塞，但应在下个 PR 处理，需作者回复 |
| 🟢 做得好 | 明确肯定，供其他人复用 |

评审意见要求：**一条意见 = 一个问题 + 一个位置 + 一个可执行建议**。
反例："这块不太好"；正例："`VoteApplicationService#retract` 里 `authorIdOf` 又查了一次库，建议把 target 聚合传进来，避免二次查询"。

---

## 1. 正确性（最高优先级）

- [ ] 🔴 聚合是否**只有业务方法能改变状态**？有没有偷偷加 setter 或 public 字段？
- [ ] 🔴 新增/修改的业务规则，是否对应一条 `INV-*` 编号？没有编号说明还没想清楚。
- [ ] 🔴 **跨聚合的一致性**是否放错位置？例如"答案属于本问题"必须在应用服务校验，不能塞进 Question 聚合。
- [ ] 🔴 领域事件是否在**聚合状态真正改变之后**才登记？失败路径会不会误发事件？
- [ ] 🔴 事件监听是否用 `AFTER_COMMIT`？回滚的事务不能产生副作用。
- [ ] 🔴 幂等键（如 `eventId`）是否**由业务标识构造**，而不是随机 UUID？
- [ ] 🔴 金额/分值/票数这类"可正可负"的字段，是否有下限/上限守卫？

**本项目实例**：Sprint 3 改判采纳时，事件最初只带 `previousAcceptedAnswerId`，评审指出"声誉侧无法反查作者，旧作者 +15 扣不掉"，改为携带 `previousAnswerAuthorId`。

---

## 2. 可读性

- [ ] 🟡 类名/方法名是否用统一语言（`Question` 而不是 `Post`，`Acceptance` 而不是 `Choose`）？
- [ ] 🟡 一个方法是否只做一件事？超过 40 行是否值得拆？
- [ ] 🟡 魔法数字是否提取为常量（`MAX_TAGS`、`UPVOTE_POINTS`）？
- [ ] 🟡 注释是否解释「为什么」而不是复述「做了什么」？
- [ ] 🟡 是否能从 Javadoc 看出这个方法对应哪条不变式/哪个故事？

---

## 3. 可测性

- [ ] 🔴 新增业务逻辑是否有**聚合级单元测试**（纯内存、毫秒级）？
- [ ] 🔴 测试是否断言了**行为**而不是实现（断言"事件被发出"，不是"方法被调用两次"）？
- [ ] 🟡 是否用 `ArgumentCaptor` 验证副作用（发事件、写库、调用外部端口）？
- [ ] 🟡 是否有"永远为真"的无效断言（`assertNotNull(new Object())` 这类）？发现即删。
- [ ] 🟡 新增接口是否有集成测试覆盖正常路径 + 至少一条失败路径？
- [ ] 🟡 时间相关逻辑是否用 `Clock` 注入，而不是 `Instant.now()`？否则测试会不稳定。

---

## 4. 安全

- [ ] 🔴 密码/令牌是否只以哈希形式落库？日志里有没有泄露？
- [ ] 🔴 请求参数是否经过 Bean Validation + 领域校验双层校验？
- [ ] 🔴 错误响应是否泄露堆栈/内部表名？统一走 `GlobalExceptionHandler`。
- [ ] 🟡 跨上下文引用是否只传 ID，避免把 User 对象塞进问答上下文？
- [ ] 🟡 标签、正文等用户输入是否有长度与字符集限制，防止存储放大攻击？

---

## 5. 性能

- [ ] 🟡 列表查询是否走索引？（本项目：`question_tag(tag, question_id)`）
- [ ] 🟡 是否引入 N+1 查询？例如循环里查作者信息。
- [ ] 🟡 事件处理是否在事务内做了重活（网络调用、大量写）？应放 `AFTER_COMMIT`。
- [ ] 🟡 热点行是否会成为写瓶颈？（票数投影就是为此拆出去的）

**本项目实例**：`ReputationRepositoryAdapter#save` 每次保存遍历全部明细并逐条 `existsByEventId`，明细多时是 N 次查询；已在 ADR-003 记录，Sprint 4 改为批量查询 + 增量写入。

---

## 6. 风格与工程规范

- [ ] 🔴 `mvn verify` 是否通过（含 Checkstyle 与 JaCoCo 门禁）？
- [ ] 🔴 是否破坏模块边界？（`co-qa` 的 pom 里绝不允许出现 `co-identity` / `co-reputation`）
- [ ] 🟡 是否新增了未使用的 import、未使用的私有方法？
- [ ] 🟡 数据库迁移是否**只追加**（V3、V4…），没有改历史脚本？
- [ ] 🟡 是否同步更新了 `docs/api/openapi.yaml` 与 README？
- [ ] 🟡 提交信息是否说清"为什么"，并关联故事编号（US-xx）？

---

## 7. 合并前最后三问

1. **这条改动如果明天出故障，别人能不能只看代码就定位？**（日志、错误码、traceId 是否够）
2. **删掉这段代码，哪个测试会红？**（删了没测试红 = 这段没被验证）
3. **它和 Lab 3 的聚合清单/术语表还对得上吗？**（对不上要么改代码，要么改文档并在 ADR 说明）
