## 1. 系统组成

| 组件 | 容器名 | 端口 | 说明 |
|---|---|---|---|
| Nginx（前端 + 反代） | `co-nginx` | 80（对外） | 静态资源、`/api` 反代到 app、SPA fallback |
| Spring Boot 后端 | `co-app` | 8080（仅内网） | 非 root 用户运行，健康检查 `/actuator/health/readiness` |
| MySQL 8.4 | `co-mysql` | 3306（仅内网） | 数据卷 `mysql-data`，Flyway 自动迁移 |
| Redis 7 | `co-redis` | 6379（仅内网） | Sprint 4 预留缓存，当前业务不依赖 |
| Prometheus | `co-prometheus` | 127.0.0.1:9090 | 抓取 `/actuator/prometheus`，15s 一次 |
| Grafana | `co-grafana` | 127.0.0.1:3000 | 看板「CampusOverflow · 生产概览」 |

所有容器在同一 `campus-overflow_backend` 桥接网络内，用**服务名**互相访问（`mysql`、`app`、`prometheus`）。
监控端口只绑定 `127.0.0.1`，通过 SSH 隧道访问，不直接暴露公网。

## 2. 首次部署

```bash
# 1) 代码与配置
git clone https://github.com/hbuas-se-2026fall/cs2412-team12-campus-overflow.git /opt/campus-overflow
cd /opt/campus-overflow
cp .env.example .env
vi .env          # 必改：MYSQL_ROOT_PASSWORD / MYSQL_PASSWORD / GRAFANA_ADMIN_PASSWORD

# 2) 构建并启动（首次 3–5 分钟）
docker compose up -d --build

# 3) 等健康检查通过
watch -n 2 'docker compose ps'
# 期望：mysql (healthy) → app (healthy) → nginx (running)

# 4) 验证
curl -fsS http://127.0.0.1/actuator/health          # {"status":"UP"}
curl -fsS http://127.0.0.1/api/v1/tags | head -c 200
curl -fsS http://127.0.0.1/ | head -n 5
```

## 3. 日常启停

| 操作 | 命令 | 说明 |
|---|---|---|
| 启动全部 | `docker compose up -d` | 已有镜像，秒级 |
| 停止全部 | `docker compose stop` | 保留容器与数据 |
| 停止并删除容器 | `docker compose down` | 保留数据卷 |
| 重启单个服务 | `docker compose restart app` | 改配置后常用 |
| 查看状态 | `docker compose ps` | 关注 healthy 列 |
| 跟踪日志 | `docker compose logs -f --tail=200 app` | 后端 |
| 查看 Nginx 日志 | `docker compose logs -f nginx` | 5xx 排查 |
| 进入容器 | `docker compose exec app sh` | 调试用，生产慎用 |

> 后端启用了 `server.shutdown: graceful` 与 20s 优雅停机；
> `docker compose restart` 会先发 SIGTERM，正在处理的请求有机会完成。

## 4. 发布与回滚

### 4.1 正常发布（CI 自动）

1. 合并到 `main` → CI（测试/覆盖率/Checkstyle）通过；
2. `images` Job 构建并推送 `ghcr.io/<org>/<repo>/backend:sha-xxxx` 与 `:latest`；
3. `deploy` Job SSH 到服务器执行 `docker compose pull app nginx && up -d --no-deps app nginx`；
4. smoke test 轮询 `/actuator/health/readiness`，失败则退出码 1 并打印日志。

### 4.2 手动发布

```bash
cd /opt/campus-overflow
export APP_IMAGE=ghcr.io/hbuas-se-2026fall/cs2412-team12-campus-overflow/backend:sha-abc1234
docker compose pull app && docker compose up -d --no-deps app
```

### 4.3 回滚（镜像级）

```bash
# 1) 查上一个可用 tag
docker images | grep backend
# 或看 GitHub Actions 的 images Job 输出

# 2) 用旧 tag 重启，只动 app
APP_IMAGE=ghcr.io/.../backend:sha-<上一个> docker compose up -d --no-deps app

# 3) 确认
curl -fsS http://127.0.0.1/actuator/health/readiness
```

> 回滚**不回滚数据库**：Flyway 只追加迁移，旧镜像仍能读新表结构（我们保证只做加法）。
> 若迁移必须破坏兼容，走"先加列、双写、再删列"的三步发布，见 §8。

## 5. 监控与告警

```bash
# SSH 隧道（本地浏览器访问）
ssh -L 9090:127.0.0.1:9090 -L 3000:127.0.0.1:3000 user@<server>
# 然后打开 http://localhost:3000 → 看板 CampusOverflow · 生产概览
```

| 指标 | PromQL（看板已内置） | 阈值 |
|---|---|---|
| QPS | `sum(rate(http_server_requests_seconds_count[1m]))` | — |
| p95 延迟 | `histogram_quantile(0.95, sum by (le) (rate(..._bucket[5m])))` | > 500ms 告警 |
| 5xx 比例 | `sum(rate(...{status=~"5.."}[5m])) / sum(rate(...[5m]))` | > 1% 告警 |
| JVM 堆 | `sum(jvm_memory_used_bytes{area="heap"}) / sum(jvm_memory_max_bytes{area="heap"})` | > 90% 告警 |
| 连接池 | `hikaricp_connections_active/idle/pending` | pending 持续 > 0 |
| 业务量 | `campusoverflow_questions_posted_total` 等 5 个计数器 | 看趋势 |

告警规则文件：`deploy/prometheus/alerts.yml`（4 条：p95、5xx、实例下线、堆占用）。

### 排查顺序（收到告警时）

1. `docker compose ps` —— 容器是否 healthy；
2. `docker compose logs --tail=200 app | grep -i error`；
3. `curl http://127.0.0.1/actuator/health` —— 是否 DB 掉线；
4. Prometheus `/alerts` 页面看告警状态；
5. 数据库：`docker compose exec mysql mysql -uroot -p -e "show processlist"`。

## 6. 备份与恢复

### 6.1 每日备份（服务器 crontab）

```bash
# 凌晨 3:10 备份，保留 14 天
10 3 * * * cd /opt/campus-overflow && \
  docker compose exec -T mysql sh -c 'mysqldump -uroot -p"$MYSQL_ROOT_PASSWORD" --single-transaction --routines campus_overflow' \
  | gzip > /opt/backup/campus_overflow_$(date +\%F).sql.gz && \
  find /opt/backup -name 'campus_overflow_*.sql.gz' -mtime +14 -delete
```

### 6.2 恢复

```bash
gunzip -c /opt/backup/campus_overflow_2026-11-23.sql.gz \
  | docker compose exec -T mysql sh -c 'mysql -uroot -p"$MYSQL_ROOT_PASSWORD" campus_overflow'

# 恢复后重启后端（清理连接池缓存）
docker compose restart app
```

### 6.3 卷级备份

```bash
docker run --rm -v campus-overflow_mysql-data:/data -v /opt/backup:/backup alpine \
  tar czf /backup/mysql-volume-$(date +%F).tgz -C /data .
```

## 7. 常见故障处置

| 现象 | 可能原因 | 处置 |
|---|---|---|
| 访问域名 502 | app 未 healthy / 崩溃 | `docker compose ps`；`logs app`；确认 MySQL healthy |
| 访问 404（刷新页面） | Nginx 未配置 SPA fallback | 确认 `frontend/nginx.conf` 有 `try_files $uri /index.html`，重建 nginx 镜像 |
| 接口 504 | 慢查询 / 连接池耗尽 | 看 p95 与 `hikaricp_connections_pending`；`show processlist` 找长事务 |
| 启动报 `Flyway ... failed` | 迁移脚本与库状态不一致 | 看 `flyway_schema_history`；按 Lab 6 记录清理失败记录后重跑；**不要**手工改历史脚本 |
| `Communications link failure` | MySQL 未就绪 / 密码错 | 确认 `mysql` healthy；核对 `.env` 的 `MYSQL_PASSWORD` 与 `DB_PASSWORD` 一致 |
| 容器反复重启，日志 OOM | 堆太小 / 内存泄漏 | 调 `JAVA_OPTS=-XX:MaxRAMPercentage=75`；看堆曲线；`docker stats` |
| 磁盘写满 | 日志/镜像/备份堆积 | `docker system df`；`docker image prune -f`；清理 `/opt/backup` 旧文件 |
| 80 端口被占用 | 已有 Nginx/Apache | `ss -lntp \| grep :80`；改 `HTTP_PORT` 或停旧服务 |
| Grafana 无数据 | Prometheus 抓取失败 | 打开 Prometheus `/targets` 看 app 是否 UP；检查网络与服务名 |
| 推送镜像 403 | GHCR 权限/未登录 | `docker login ghcr.io -u <user> -p <PAT>`；确认包可见性 |

## 8. 变更与迁移规范

1. **迁移只追加**：新增 `V3__*.sql`，不改 V1/V2；
2. **破坏性变更三步走**：加新列（双写）→ 数据回填 → 删旧列，分三次发布；
3. **发布前**：`mvn verify` 全绿 + 本地 `docker compose up` 冒烟；
4. **发布后**：观察 10 分钟 p95 / 5xx / 业务计数器，异常立即回滚镜像。

## 9. 安全基线

- 容器内**非 root**（后端 `USER app`）；
- 数据库与监控端口**不映射公网**（Prometheus/Grafana 绑 `127.0.0.1`）；
- 密码只存 `.env`（已 gitignore）或 CI Secrets，**不进镜像、不进仓库**；
- SSH 只允许密钥登录，禁用密码登录；
- GHCR 使用最小权限 token（`read:packages`）；
- 定期 `docker compose pull` 基础镜像并重建（打安全补丁）。
