# Lab 8 部署方案（CI/CD + 容器化 + 监控）

> 第 12 组 · CampusOverflow · Sprint 4 上线版
> 配套文件：`Dockerfile`、`frontend/Dockerfile`、`frontend/nginx.conf`、`docker-compose.yml`、`deploy/prometheus/*`、`deploy/grafana/*`、`.github/workflows/ci.yml`

---

## 1. 目标与范围

| Lab 8 目标 | 本方案对应实现 |
|---|---|
| 完整 CI/CD：push → 自动部署测试环境 | GitHub Actions：`backend` / `frontend` → `images`（GHCR）→ `deploy`（SSH） |
| Docker 多阶段构建 | 后端 `maven → temurin-jre-alpine`；前端 `node → nginx-alpine` |
| docker-compose 一键启动 | `docker compose up -d --build` 起 6 个服务 |
| Prometheus + Grafana，≥5 个核心指标 | 5 个业务计数器 + HTTP 延迟/错误率 + JVM + 连接池（10+） |
| 上线到课程环境，校园网域名访问 | Nginx 80 端口 + 子域名解析 + 可选 certbot TLS（见 §6） |

## 2. 部署架构

```
                     校园网 / 公网
                          │
                   team12.<课程域名>
                          │  :80 / :443
                 ┌────────▼─────────┐
                 │  co-nginx        │  静态资源 + /api 反代 + SPA fallback
                 └────────┬─────────┘
                          │  后端私有网络（docker network: backend）
                 ┌────────▼─────────┐        ┌──────────────────┐
                 │  co-app :8080    │◄───────┤ Prometheus :9090 │  抓取 /actuator/prometheus
                 │  Spring Boot     │        └────────┬─────────┘
                 └───┬──────────┬───┘                 │
                     │          │                     ▼
              ┌──────▼───┐  ┌───▼──────┐        ┌──────────────┐
              │ co-mysql │  │ co-redis │        │ Grafana :3000│
              │  8.4     │  │  7       │        └──────────────┘
              └──────────┘  └──────────┘
```

- **唯一对外端口是 80/443**；MySQL、Redis、Prometheus、Grafana 都不映射公网；
- Prometheus/Grafana 绑定 `127.0.0.1`，通过 SSH 隧道访问（`ssh -L 3000:127.0.0.1:3000 ...`）；
- 容器之间用服务名互访，不做跨主机网络（规避 Lab 8"常见陷阱"第 2 条）。

## 4. GitHub Secrets 清单

在仓库 `Settings → Secrets and variables → Actions` 配置：

| Secret | 必填 | 说明 |
|---|---|---|
| `DEPLOY_HOST` | 是（部署时） | 测试服务器 IP 或域名 |
| `DEPLOY_USER` | 是 | SSH 用户（建议专用 `deploy` 用户） |
| `DEPLOY_SSH_KEY` | 是 | 私钥（公钥已在服务器 `~/.ssh/authorized_keys`） |
| `DEPLOY_PATH` | 是 | 服务器项目目录，如 `/opt/campus-overflow` |
| `PUBLIC_BASE_URL` | 否 | 对外地址，用于公网 smoke test，如 `https://team12.example.edu.cn` |
| `SONAR_TOKEN` | 否 | Lab 7 的 SonarQube 扫描 |
| `SONAR_HOST_URL` | 否 | SonarQube 地址 |

> `GITHUB_TOKEN` 由 Actions 自动提供，用于推送/拉取 GHCR 镜像，**不需要**手动配置。
> 未配置 `DEPLOY_HOST` 时，`deploy` Job 的步骤会自动跳过，流水线保持绿色。

## 5. 流水线阶段

```
push / PR
   │
   ├─ backend：mvn clean verify（Checkstyle + 112 个测试 + JaCoCo + 覆盖率门禁）
   ├─ frontend：pnpm lint / typecheck / build
   │
   └─（仅 main push）
        ├─ images：docker build & push
        │     ghcr.io/<org>/<repo>/backend:sha-xxxx / :latest
        │     ghcr.io/<org>/<repo>/frontend:sha-xxxx / :latest
        └─ deploy：SSH → docker compose pull app nginx → up -d --no-deps
              └─ smoke test：轮询 http://127.0.0.1/actuator/health/readiness（最长 90s）
                    └─ 公网 smoke test（配置了 PUBLIC_BASE_URL 时）
```

镜像使用 `type=gha` 缓存，二次构建明显更快；Backend 镜像先 `dependency:go-offline` 再拷源码，改代码不会重下依赖。

## 6. 域名、TLS 与访问

### 6.1 域名解析

课程统一部署环境会给每队一个子域名（如 `team12.<课程域名>`）。在 DNS 控制台添加 A 记录指向服务器公网 IP。

### 6.2 TLS（可选，但上线建议）

```bash
# 服务器上
apt install -y certbot
certbot certonly --standalone -d team12.<课程域名>
# 证书路径：/etc/letsencrypt/live/team12.<课程域名>/
```

在 `frontend/nginx.conf` 增加 443 server 块并挂载证书卷；或更简单：在宿主机前置一层 Nginx/Caddy 做 TLS，容器仍监听 80。

### 6.3 校园网访问验证

```bash
curl -I http://team12.<课程域名>/                 # 200，text/html
curl -s http://team12.<课程域名>/api/v1/tags      # JSON
curl -s http://team12.<课程域名>/actuator/health  # {"status":"UP"}
```

## 7. 首次部署步骤（服务器）

```bash
# 1) 安装 Docker 与 Compose 插件
curl -fsSL https://get.docker.com | sh
docker compose version

# 2) 拉代码（或只拉 compose 与 deploy 目录）
git clone https://github.com/hbuas-se-2026fall/cs2412-team12-campus-overflow.git /opt/campus-overflow
cd /opt/campus-overflow

# 3) 配置
cp .env.example .env
vi .env                               # 改 3 个密码
chmod 600 .env

# 4) 登录 GHCR（私有包需要）
echo "$GHCR_TOKEN" | docker login ghcr.io -u <github-user> --password-stdin

# 5) 启动（首次用本地构建；后续用 CI 推送的镜像）
docker compose up -d --build

# 6) 验证
docker compose ps
curl -fsS http://127.0.0.1/actuator/health
```

### Redis 的定位（诚实说明）

`docker-compose.yml` 里包含 `redis` 服务（实验要求"完整 compose"），但**当前业务代码不依赖 Redis**：
它预留给 Sprint 4 的会话/热点缓存。因此 Redis 故障不会影响问答主流程；
等接入时再在 `application.yml` 增加 `spring.data.redis.*` 并把缓存逻辑放进应用层。

## 8. 回滚

| 场景 | 操作 |
|---|---|
| 新版本接口异常 | `APP_IMAGE=...:sha-<上一个> docker compose up -d --no-deps app` |
| 前端白屏/资源 404 | 同上，把 `FRONTEND_IMAGE` 指回上一个 tag |
| 迁移脚本失败 | 按 `docs/lab6/验证记录.md` §2 的清理步骤处理；**不要**改历史脚本，用 V3 修正 |
| 整体回退 | `git checkout <上一个发布 commit>` + `docker compose up -d --build` |

镜像保留策略：GHCR 保留所有 `sha-*` tag，`latest` 只指向最近一次成功发布。

## 9. 本机与生产环境的差异（必须知道）

| 项 | 本机（开发） | 生产（服务器） |
|---|---|---|
| 启动方式 | `java -jar` / `pnpm dev` | `docker compose up -d` |
| 数据库 | 本机 MySQL 或 H2 | 容器 MySQL 8.4 + 数据卷 |
| 反向代理 | Vite dev server proxy | Nginx |
| 配置来源 | `application.yml` 默认值 | `.env` → 环境变量 |
| 监控 | `/actuator/prometheus` 可 curl | Prometheus 抓取 + Grafana 看板 |

> 本仓库的开发机没有 Docker，因此镜像构建与 `docker compose up` **未在本机执行**；
> 流水线的 `images` Job 在 GitHub Actions 上真实构建，服务器上真实部署。详见 `docs/lab8/验证记录.md`。

---

## 10. 与 Lab 7 门禁的衔接

- `mvn verify` 里的 Checkstyle / JaCoCo / 覆盖率门禁在 CI 中先跑，**失败就不会构建镜像**；
- SonarQube（可选）在 `backend` Job 中执行，质量门禁不通过同样阻断后续 `images`；
- 这样保证"能部署的镜像一定是过了质量门禁的镜像"。
